## Контекст

Ти працюєш у проекті **FinNavis** — особистий фінансовий REST API, один власник, self-hosted, без
автентифікації.

Стек: .NET 10 / C# 14 (nullable on, `TreatWarningsAsErrors`), xUnit + AwesomeAssertions. Чотири
кільця: `Domain` → `Application` → `Infrastructure` → `Presentation`, залежності тільки всередину.

Цей зріз — **адаптери Infrastructure, композиційний корінь і перші use cases**: п'ять репозиторіїв
з unit of work, три запити читання, реєстрація в DI і чотири сценарії по рахунках. **Потрібен
запущений Docker.** Домен, конфігурації EF і міграція вже є — T01–T12 закриті.

Прочитай перед роботою:

4. Зроби задачу. Дотримуйся конвенцій `CLAUDE.md`.
5. Перевірка: `./build.sh build` і `./build.sh test` мають бути зеленими. Warnings тут це помилки.
6. Один atomic commit на задачу, Conventional Commits за `.claude/rules/git.md`. Гілка вже створена,

   це була остання з шести задач: тоді спершу виконай крок 9.
8. Задача не закрилась за 3 спроби (`attempts` більше за 3) → постав `blocked` у `tracker.md` і в
   `status:` у frontmatter, допиши в `tracker.md` причину одним рядком: що саме зараз не проходить
   (build, test, Docker чи пункт DoD). Створи файл `BLOCKED` у корені і вийди. Нічого не комміть —
   рішення далі за власником.

## DoD

DoD кожної задачі — це чекліст `## Definition of Done` у її `T<NN>-*.md`, дослівно. Задача зроблена,
коли **кожен** пункт того чекліста виконано. Не додавай своїх критеріїв і не прибирай чужих.

Плюс жорсткі правила епіку, які діють у цьому зрізі (`_epic.md` §Risks / Hard rules, `CLAUDE.md`):

- **Читання не завантажує сутності в пам'ять.** Агрегація виконується в PostgreSQL, назад їдуть
  тільки рядки результату (ADR-0004). Баланс, історія і розріз не проходять через репозиторії.
- **Розріз ніколи не читає `transfers`.** AC-20 виконано структурно: запит просто не дивиться на цю
  таблицю (ADR-0001).
- **Група `Default` — не рядок і не сутність.** Її збирає Application з категорій без групи
  (sad.md §12). Нічого схожого не створюй і не зберігай.
- **Курсор — непрозорий рядок, який видає сервер**, а не голий UUID. `limit` від 1 до 200, за
  замовчуванням 50. Фільтр за категорією повністю виключає перекази. Це вже вирішено в
  `api-sync-report.md`.
- **EF:** `AsNoTracking()` для читання, `AsSplitQuery()` для колекцій, проєкція в DTO замість
  вибірки зайвих колонок.
- **Гроші — `decimal`**, ніколи `float` чи `double`.
- **`CancellationToken` проходить через кожен async-виклик.**
- **Залежності вказують тільки всередину.** `Infrastructure.csproj` містить **тільки**
  `Application`; Domain приходить транзитивно, і це навмисно. Application не знає про EF Core, HTTP
  чи PostgreSQL. `tests/FinNavis.ArchitectureTests` це перевіряє.
- **Юніт-тести не чіпають БД і мережу.** Тести T18 — юніт-тести. Інтеграційні тести T13–T16 йдуть
  через фікстуру Testcontainers з T02.
- **Формулювання відмови береться з AC у `PRD.md` дослівно**, не вигадується.
- Жодного реального connection string, пароля чи ключа в закоміченому файлі.

Окремо про коди помилок. T18 у своєму DoD називає `Account.HasRecordedHistory`,
`Account.DuplicateName` і `Account.NotFound` — пиши рівно ці рядки. Реєстр помилок і конверт
`{code, message, details?}` — це T24, сюди він не входить. ADR щодо модуля для `*.NotFound` (задача
T04) ще не написаний: **не вирішуй це питання**, просто використай назви, які вже стоять у DoD.

## Відоме про оточення

- `./build.sh run` у DoD T17 піднімає API проти compose-стека з T01. Для нього потрібен
  git-ignored `.env` у корені; перелік змінних — у шапці `docker-compose.yml`.
- Design-time фабрика `FinNavisDbContextFactory` читає рядок підключення зі змінної оточення
  `ConnectionStrings__FinNavisDb`. Чи пробрасує `dotnet ef` змінні з `launchSettings.json` — не
  перевірено. Якщо `./build.sh db-update` впаде на хості `connection-string-is-unset.invalid`,
  задай змінну явно; це не привід міняти фабрику.
- Папка `src/FinNavis.Infrastructure/Persistence/Migrations` позначена в `.editorconfig` як
  згенерований код. Нові файли поза нею підпорядковуються звичайним правилам стилю.
