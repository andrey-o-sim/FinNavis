# 0005 — Use UUID v7 primary keys generated in the Application layer

- **Status:** Accepted
- **Date:** 2026-10-16
- **Deciders:** Andrey Simonenko

## Context

core-ledger creates the first five tables in a database that currently has none: accounts,
categories, category groups, transactions and transfers. The type of their primary keys has to be
chosen before the first migration is written, because changing it afterwards means migrating every
table and backfilling every foreign key that points at them.

Two features already queued behind this one shape the choice. csv-import builds a batch of rows and
the links between them from a file, and the planned message capture creates an expense from an
incoming Telegram or email message.

## Decision drivers

- `SPEC.md` "Safe schema change" — any change reaching a database that already holds rows must lose
  or alter no row. A primary-key type change cannot meet that bar cheaply.
- PRD §6 — period breakdown p95 ≤ 500 ms and history page p95 ≤ 400 ms, both served by indexed
  queries, so index behaviour matters.
- CONTEXT.md *Import run* — one load of one file is read back or undone as a whole, which is easier
  when the rows and their links can be built before anything is written.
- ADR-0006 — a nullable external reference is added now so the next features need no backfill; the
  same reasoning applies to the key itself.
- .NET 10 ships `Guid.CreateVersion7()`, so a time-ordered UUID costs nothing extra to produce.

## Considered options

1. **UUID v7, generated in the Application layer**, stored as PostgreSQL `uuid`. The value embeds a
   timestamp, so keys sort by creation time.
2. **`bigserial`** — auto-increment integers generated by PostgreSQL on insert.
3. **UUID v4** — random UUIDs, generated anywhere.

## Decision outcome

**Chosen: option 1, UUID v7 generated in the Application layer.**

The deciding property is that the identifier exists *before* the row is written. csv-import can
assemble a whole run — its transactions and the links between them — in memory and commit it in one
unit of work, and a later message-capture or public API can generate an id without a round trip.
With `bigserial` the id only exists after the insert, so every one of those callers has to write
first and link second.

UUID v7 is chosen over v4 because it is time-ordered. Random v4 keys scatter inserts across the
B-tree and fragment the index, which is the well-known reason v4 makes a poor primary key; v7 keeps
the insert point at the end of the index and keeps range scans by creation time cheap. Since .NET 10
provides `Guid.CreateVersion7()` directly, that benefit is free.

Generation sits in the Application layer rather than in Domain or the database, because assigning an
identity is an orchestration step: Domain stays free of any clock or generator it does not own, and
PostgreSQL is treated as storage rather than as a source of values.

## Consequences

**Positive**
- Identifiers exist before insert, so a batch of related rows can be built and committed as one
  unit — the shape csv-import needs.
- Keys are time-ordered, so index locality is good and "most recent first" history paging can use
  the key rather than needing a separate sort column.
- Identifiers are globally unique, so exported data from two installations could be merged without
  collision.
- An exported file does not reveal how many entries exist, which sequential ids would.

**Negative**
- 16 bytes per key instead of 8, repeated in every foreign key and index. At roughly 20 000 rows
  this is a few hundred kilobytes and does not matter; at a much larger scale it would.
- Identifiers are long and unfriendly in a URL or a log line, and are impossible to read out loud or
  compare by eye while debugging.
- A UUID v7 leaks its creation timestamp. For a single-owner self-hosted ledger this is not a
  concern, but it is a real property of the format.

**Neutral**
- Storing them as native PostgreSQL `uuid` rather than text keeps them 16 bytes and comparable; this
  is an entity-configuration detail, fixed here so it is not re-litigated per table.
- Nothing stops a later feature from accepting a caller-supplied id, since the type already allows
  it. That would be new scope, not a migration.
