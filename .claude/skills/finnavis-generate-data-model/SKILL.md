# Data model — solo project

Stage 04. `finnavis-architecture-design` settles the aggregates and the ports;
`finnavis-complete-sequence-diagrams` settles which queries the runtime actually makes. This skill
turns both into tables, columns and indexes — and records the decisions neither upstream document
was in a position to make.

Three outputs:

- `docs/features/<slug>/data-model.md` — ER diagram, decisions, entities, indexes, seeds, fixtures.
- `docs/features/<slug>/migrations/*.up.sql` + `.down.sql` — **a reference spec, never applied**.
- `docs/features/<slug>/_audit/data-model-<date>.md` — divergences, drift, self-check, follow-ups.

## The one thing to understand before anything else

**EF Core owns the real migration here. The staged SQL is a specification of what it must produce.**

`CLAUDE.md` and `.claude/rules/migrations.md` fix migrations as EF Core, generated by
`./build.sh migrate <Name>`. EF keeps a `ModelSnapshot.cs` of the schema it believes exists, so a
table created by hand-written SQL is invisible to it and the next `dotnet ef migrations add` would
create it a second time. The two cannot be mixed.

So the staged pair states the exact DDL the feature must end up with. At `implement-tasks` the
entities and their `IEntityTypeConfiguration<T>` files are written, `./build.sh migrate` generates
the real migration, and `dotnet ef migrations script` is diffed against the spec. A difference means
the configuration or the spec is wrong — resolved before anything is applied.

Every `.up.sql` opens with that fact, so a file found on its own cannot be mistaken for something
runnable:

```sql
-- REFERENCE SPEC — not an applied migration. See .claude/rules/migrations.md.
```

## When to use

- "модель данных для `<slug>`", "схема для `<slug>`", "какие индексы нужны", "сгенерируй миграции",
  and the same asks in any language the user writes in.
- `/finnavis-generate-data-model <slug>` as an explicit call.
- After the SAD's §6 is complete — the flows are where the indexes come from.
- `--drift-only` — compare an existing `data-model.md` against the PRD, the SAD and the code. No
  generation, just findings.

## When not to use

- **`data-model.md` exists and every entity in it has a staged pair.** Re-running overwrites a
  reviewed design. Use `--drift-only`, or edit the entity that changed.
- **To write the EF Core entity configurations.** That is `implement-tasks`. This stage designs; it
  does not touch `src/`.
- **To decide an aggregate boundary.** SAD §5 settled that. If it is wrong, fix it there — a schema
  built on a wrong aggregate is a schema that has to be rebuilt.

## Inputs

- `<slug>` · `PRD.md` (§4 user stories, §5 acceptance criteria, §6.1, §8 open questions, §9 data
  impact) · `sad.md` (§5 aggregates and ports, §6 flows and the Notes-flagged index hints, §8, §11)
  · `docs/features/<slug>/CONTEXT.md` (the feature's terms, its `## Invariants` — what a constraint
  exists to protect — and the link to `docs/GLOSSARY.md`, where those terms are defined) —
  **required**.
- `CLAUDE.md`, `ARCHITECTURE.md`, `.claude/rules/migrations.md`, `docs/features/<slug>/adr/` — read
  every run. The rules file is the house style; it is read, never written.
- **Every earlier feature's `data-model.md`, staged migrations and Accepted ADRs** — they are the
  baseline this feature adds to, not a reference. `core-ledger`'s ADR-0006 already put
  `external_ref` on `transactions` for exactly this reason.
- `src/FinNavis.Domain/`, `src/FinNavis.Infrastructure/Persistence/` — read for drift. Both are a
  skeleton until the first feature is built; that is a normal, reported outcome, not a failure.

## Protocol

### 0. Setup (read-only)

Read the gates, the rules file, the ADRs, and every earlier feature's `data-model.md`. Read the
three templates. Then establish the **baseline schema** — what already exists:

1. `src/FinNavis.Infrastructure/Persistence/Migrations/` — if it holds migrations, that is the real
   schema and the baseline.
2. Otherwise the staged specs under `docs/features/*/migrations/` — the design agreed so far.
3. Say in the audit which of the two was used. They diverge the moment a feature is built, and a
   delta computed against the wrong one is a delta against a document rather than a database.

### 0.5. One question (AskUserQuestion — mandatory)

**Commits** — *commit it yourself* / *just print the command* (recommended). Depth is not asked:
this stage has no dial, and everything it decides is written down to be reviewed.

### 1. Entities and their columns

Aggregates come from SAD §5 — never re-derived, never re-asked. One table per aggregate, plus the
tables an aggregate owns. Types, bounds and nullability →
[references/columns-and-types.md](references/columns-and-types.md).

Each column traces to something: an acceptance criterion, an ADR, a `docs/GLOSSARY.md` term, or a decision
this document makes in §"Decisions taken". A column that traces to nothing is a column nobody asked
for — drop it or make it a decision with a reason.

### 2. Indexes

Every index is justified by a concrete query from a SAD §6 flow, plus the index hints the sequences
stage left in §6's Notes-flagged block. Method, the FK rule, the negative list and what
`CONCURRENTLY` costs → [references/indexes.md](references/indexes.md).

### 3. Decisions the PRD and SAD left open

The schema forces answers the upstream documents did not have to give: how long is a note, is a date
a calendar day or a timestamp, is a name unique. Each one goes into §"Decisions taken in this
document" as a decision with its reason — not buried in a table cell.

Then find the **open questions due by this stage** in PRD §8 and SAD §11. Answer them here, and show
the user the exact edit that makes §8 and §11 stop reading as open. Edit only after a yes. Two
documents that disagree about whether a question is settled is how a closed question gets reopened
six months later.

### 4. Write `data-model.md`

From [`templates/data-model.md`](templates/data-model.md). Lint the `erDiagram` →
[references/mermaid-lint.md](references/mermaid-lint.md) before moving on; a broken diagram renders
as an error box and nobody fixes an error box in a file they are only reading.

### 5. Write the staged spec

From [`templates/migration-spec.sql`](templates/migration-spec.sql), into
`docs/features/<slug>/migrations/` — one `<YYYYMMDDhhmmss>_<verb>_<entity>.up.sql` plus its
`.down.sql` per table or small aggregate. Never into `src/FinNavis.Infrastructure/`.

- `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ON CONFLICT DO NOTHING` on seeds.
- Comment each non-obvious column with the AC, ADR or decision behind it. The spec is read by a
  human diffing it against EF's output; a bare DDL line gives them nothing to check against.
- **Changing a table an earlier feature defined** follows the zero-downtime rules in
  `.claude/rules/migrations.md` — three steps for a new NOT NULL or a rename, `CONCURRENTLY` for a
  new index. Apply them, and add one line to the audit saying what the ceremony costs here (three
  migrations instead of one) and that it buys safety for a database that does not exist yet. The
  rule holds; the user decides whether to keep paying for it.

### 6. Self-check — four checks, all four must pass

Per `.claude/rules/migrations.md`:

- **Naming.** Plural `snake_case` tables, `<timestamp>_<verb>_<entity>.(up|down).sql` files.
- **Reversibility.** Every `CREATE` has its `DROP`, every `ADD COLUMN` its `DROP COLUMN`; drops
  ordered indexes-before-table.
- **FK indexes.** Every `REFERENCES other_table(id)` has an index with that column leading.
- **Forbidden features.** Grep for `CHECK (`, `CREATE TRIGGER`, a stored procedure, and `DEFAULT '`
  followed by a business literal. The only `DEFAULT` allowed is `now()` on a timestamp.

A failure is fixed or surfaced, never quietly committed.

### 7. Drift and the audit report

Three drift directions and the report structure →
[references/drift-and-audit.md](references/drift-and-audit.md). The third direction — a constraint
no acceptance criterion asks for — is the one that catches real gaps, and the generic version of
this stage does not look for it.

### 8. Handoff

```md
## ✅ finnavis-generate-data-model — <slug>

**What I did**
- `data-model.md` — <N> tables, <M> indexes, <D> decisions recorded
- <N×2> staged spec files under `migrations/` — reference spec, not applied
- audit report — <X> divergences, <Y> drift findings, self-check <n>/4
- <Q> open questions closed; PRD §8 and SAD §11 updated / left for you

**Review before continuing**
- `data-model.md` §"Decisions taken" — the choices nobody else made
- the indexes table, and the list of the ones deliberately not created
- the audit's drift findings — a constraint with no AC behind it is a PRD gap, not a schema detail

**Run next**
1. `/clear`
2. then the API-contract stage, then implementation. At `implement-tasks` the spec is diffed
   against `dotnet ef migrations script` output before anything is applied
```

## Definition of Done

Each line is also the anti-pattern it rules out — the failure mode is named after the dash.

- Nothing was written into `src/FinNavis.Infrastructure/` — *this stage designs; a half-designed
  schema must not be reachable by `./build.sh db-update`*.
- Every staged `.up.sql` opens with the REFERENCE SPEC header — *a file found alone must not look
  runnable*.
- One table per SAD §5 aggregate; aggregates were read, not re-decided — *a schema on a wrong
  aggregate gets rebuilt, not patched*.
- Every column traces to an AC, an ADR, a `docs/GLOSSARY.md` term, or a recorded decision — *no column
  nobody asked for*.
- Every index names the query it serves, and the ones not created are listed with reasons — *no
  "just in case" index, and no silent re-adding of one that was already rejected*.
- Money is `NUMERIC(19,4)`, enums are strings, bounded strings are `VARCHAR(N)` — *never `float`,
  never an int-backed enum, never `TEXT` for everything* (`CLAUDE.md`).
- `created_at` only, unless a requirement actually reads a last-changed value — *`updated_at` is
  never added silently*.
- No `CHECK`, no `TRIGGER`, no stored procedure, no business `DEFAULT` — *invariants live in the
  Domain entities; the database stays dumb storage*.
- A column an earlier ADR already added is reused, not re-added — *read the earlier features first*.
- Changes to an earlier feature's table follow the zero-downtime rules, with their cost named once
  in the audit — *the rule is applied, and the user can see what it bought*.
- Open questions due at this stage are answered, and PRD §8 / SAD §11 are updated after a yes —
  *the documents do not disagree about what is settled*.
- Seeds: all three buckets addressed, "empty and here is why" counts — *a missing bucket reads as
  forgotten*. No real-looking personal data, and no real bank statement or export, anywhere.
- Self-check 4/4, `erDiagram` parses, every `<!-- TBD -->` listed in the audit with its line.
