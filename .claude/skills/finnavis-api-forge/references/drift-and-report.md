# Drift check and the sync report

Used in protocol steps 5 and 6.

The check runs in **both directions**. Forward asks "was the contract derived correctly from the
sources". Back-feed asks "does the contract need something the sources never gave it" — and a gap
found that way is a hole upstream, not a contract bug.

## The six points

Points 1–3 are **core**: a ✗ there is a `FAIL`. Points 4–6 are **supporting**: a ✗ there can be
parked as a deferral with a named next step.

### 1. Operation ↔ data model *(core, forward)*

Every schema property maps to a column in `data-model.md`. Evidence: the Section A trees — one tree
per operation, the type on each node, `name · type · conf · ← origin` on each leaf.

The tree is what makes this point checkable. A flat `operation.field` path loses the type, so a
nested array and the fields of its element type end up in unrelated rows and nobody can tell they
belong together.

The origin is read on the leaf itself, wrapped under itself when it is long — never moved to a
footnote and never shortened. The template says why.

✗ looks like: a property with no column behind it, or a property whose type disagrees with the
column (`integer` against `NUMERIC(19,4)`).

### 2. Error code ↔ definition in the repo *(core, forward)*

Every `code` the contract advertises exists once in `src/`, spelled identically.

While `src/` is a skeleton this is **✓ (deferred)**, not ✗ — list every code so `implement-tasks`
transcribes rather than re-derives. Once endpoints exist, a missing or differently-spelled code
is a real ✗.

### 3. Validation ↔ constraint *(core, forward)*

Every bound in the contract matches the column. `varchar(200)` → `maxLength: 200`. A nullable
column → `type: [string, "null"]`. A money column → `type: string` with the decimal pattern. An
enum column → the same values, as strings.

✗ looks like: a `maxLength` the model does not have, a bound looser than the column (the database
will reject what the contract accepts), or `nullable: true` anywhere.

### 4. Coverage: AC ↔ operation, entity ↔ operation *(supporting, back-feed)*

Three sweeps:

- every PRD §5 acceptance criterion maps to at least one operation or response;
- every operation maps to a §4 user story **and** at least one AC;
- every `data-model.md` entity is surfaced by at least one operation, or marked intentionally
  internal with its reason.

✗ looks like: a table nothing can create (`core-ledger`'s `category_groups` was exactly this), a
use case SAD §5 declares that no story covers, or an endpoint that exists because it felt natural.

### 5. OpenAPI ↔ sequence *(supporting, both directions)*

Every `alt`-branch in a §6 flow has a response. Every error response the contract needs has a
branch, or is listed as a **sequence gap**.

A sequence gap is normal for validation and uniqueness branches — a diagram legitimately omits them.
It is not normal for a state or ordering refusal, which is exactly what a diagram is for.

### 6. Contract ↔ the served document *(supporting, FinNavis only)*

The point the generic version of this stage does not have.

`/openapi/v1.json` is generated by ASP.NET Core from the Minimal API endpoints (`CLAUDE.md` §API).
Once `src/FinNavis.Presentation/Endpoints/` has folders, compare:

- every operation here has its `Presentation/Endpoints/<Resource>/<Operation>/` folder;
- paths, methods and status codes match;
- no endpoint exists in the code that this contract never declared;
- the error shape the code returns is the flat envelope, not `application/problem+json`.

Before implementation this is **N/A — `src/` is a skeleton**, stated plainly rather than marked ✓.
Marking an unchecked point ✓ is the failure this point exists to prevent.

## Resolving a finding

Four actions, chosen **with the user**, never alone:

| Action | When | What happens |
|---|---|---|
| **Accept as is** | The finding is real and the answer is "yes, on purpose" | Recorded in the report with its reason. No edit. |
| **Fix the contract** | The contract is the wrong artifact | Edit the YAML, re-run the point. |
| **Save as a deferral** | Real, but not now | A row in Deferrals with what, why parked, and the next step. |
| **Fix the source first** | The PRD, the SAD or the model is wrong | Stop. Name the command to run. This is the one that produces a `FAIL`. |

Never silently edit the PRD, the SAD or `data-model.md`. Those are reviewed documents, and a quiet
edit removes the review.

## Conflict table

| Conflict | What to do |
|---|---|
| A column in `data-model.md` with no story covering it | Add it with a `# unused-in-prd` note; ask the user. |
| A §6 flow that maps to no operation | Flag `# orphan-sequence`; ask — forgotten endpoint, or internal? |
| A PRD constraint that contradicts a model constraint | Take the stricter value, flag both, let the user say which document is wrong. |
| An existing contract has a field no source mentions | Keep it with `# manual-addition`; flag it. |
| A field left `data-model.md` | Keep it with `# stale`; the user removes it here or restores it there. |
| An earlier feature's contract declares the same path differently | Stop. Two contracts describing one path differently is drift that reaches the client. |

Three or more flags in one run: pause, list them, ask whether to continue or fix the sources first.

## Verdict

| Verdict | Rule |
|---|---|
| `PASS` | Scenario A, all six ✓ (point 6 may be a stated N/A), nothing parked. |
| `PASS (with deferrals)` | Core 1–3 ✓ and something parked on purpose. Every parked item has a Deferrals row. |
| `FAIL` | A core point ✗, three or more open flags, or a field with no origin. |

Derived from the checklist, never typed from a feeling. Writing `PASS` over an unresolved core ✗ is
the anti-pattern this section exists for.

The report is written **on every run, `FAIL` included**. A `FAIL` contract is still written and
still reviewable — it just does not hand off to implementation.

## Report structure

Follows [`../templates/api-sync-report.md`](../templates/api-sync-report.md):

1. Header — verdict, date, run mode, sources read with ✓/✗, scenario, contract version.
2. **Why `FAIL`** — only on a FAIL, before anything else, in two or three sentences.
3. Section A — field origins, one tree per operation, C# names and contract types.
4. Section B — the six points, each ✓ / ✓ (deferred: one line) / ✗ (one-line diagnostic) / N/A.
5. Section C — `unresolved_origins`: empty in A, listed in B.
6. Section D — Deferrals: what, why parked, next step.
7. Decisions settled at this gate — open questions from PRD §8 and SAD §11 this run closed.
8. What `--reconcile` reads first.

## Reconcile

`--reconcile` after an upstream document moved. It re-reads everything, switches B → A if
`data-model.md` arrived, tightens loose types, promotes inferred origins to column origins, and
empties `unresolved_origins`.

The load-bearing part is the last one: a field that **had** an inferred origin and now **disagrees**
with the model. That is real drift, not stale incompleteness, and it is surfaced rather than
silently overwritten.

`info.version` is never bumped silently. The user bumps it with a CHANGELOG line.
